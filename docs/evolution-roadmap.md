# Coderus 演进设计

## 1. 文档状态

- 状态：已批准（2026-08-27 修订：产品方向调整为自动化工作平台）
- 目标周期：未来三到六个月
- 产品方向：自动化研发工作平台——在统一的任务基建之上运行多种可插拔的自动化任务类型，同时具备可公开推广的开源体验
- 部署边界：单机部署、SQLite、本地 Agent 子进程

## 2. 背景

Coderus 已经具备从人工派发 Issue 到开发 Agent 修复、双 Reviewer 检视、集中修正、提交 Pull Request 和飞书通知的完整闭环，具备任务租约、通知 outbox、凭据隔离、模型短期凭据代理和签名发布等可靠性基础，并已上线基于模型的飞书只读问答助手。

下一阶段的主要问题是：

1. **模块耦合**：`web/app.py` 承担装配、路由和业务逻辑（依赖 18 个内部模块）；`forge`、`providers`、`publisher` 三个模块重叠实现平台适配；`workflow/orchestrator.py` 将全部阶段逻辑内联；飞书入口直接编排 7 个业务模块，与网页各写一遍相同用例。
2. **任务类型硬编码**：Issue 修复（RE）和 PR 检视（RV）是两套独立写死的状态机，新增任务类型没有可复用骨架，与"工作平台"的目标冲突。
3. **诊断与评测不足**：任务失败诊断成本较高，Agent 效果缺少统一评测基线。
4. **首次部署门槛**：开源用户首次部署仍需要较多人工判断，缺少环境诊断和配置向导。

后续演进优先收敛架构、建立可观测和评测基础，然后把"任务类型"提升为一等概念，使平台能够以低成本承载新的自动化任务。

## 3. 目标与非目标

### 3.1 目标

1. 模块解耦：入口、应用服务、任务编排、平台适配、基建分层清晰，降低核心模块修改风险。
2. 让任务的当前阶段、失败原因、执行证据和恢复方式清晰可见。
3. 通过固定评测集持续衡量并提高 Agent 一次修复成功率。
4. 任务类型可插拔：新增一种自动化任务只需实现阶段处理器和产物规格，不修改调度、租约、工作区、凭据等基建代码。
5. 网页、飞书和未来 API 调用同一套应用服务，权限、校验、幂等和错误行为一致。
6. 让新用户能够在普通 Linux 主机上快速完成安装和环境诊断，内部使用版和开源版保持同一套代码，仅通过配置和密钥区分环境。

### 3.2 非目标

- 不引入 PostgreSQL、消息队列或分布式 Worker。
- 不引入任意 DAG 工作流引擎；任务类型使用固定的有限阶段序列。
- 不建设多租户计费和复杂组织权限。
- 不建设通用插件市场。
- 不自动领取未经人工确认的 Issue，不自动合并 Pull Request。

## 4. 设计原则

- **单机优先**：围绕单机 SQLite 和本地进程把可靠性做到完整，不提前支付分布式复杂度。
- **固定流程**：每种任务类型使用明确的有限阶段，不设计通用工作流语言。
- **基建复用**：调度、租约、工作区、凭据、通知、发布是所有任务类型共用的底座；新任务类型只写业务阶段。
- **证据优先**：测试命令、退出码和代码差异是事实，Agent 的文字结论不能替代执行证据。
- **安全恢复**：只从明确的安全检查点恢复；具有外部副作用的操作必须先对账。
- **写操作人工确认**：助手和自动化流程可以准备写操作，但派发、检视等改变系统状态的动作必须由人确认。
- **渐进整改**：按模块逐步替换，每个阶段均可独立测试、发布和回滚。

## 5. 目标架构

```text
网页 / 飞书 / API 入口（解析、鉴权、呈现）
      |
      v
应用服务层（派发、检视、查询、取消等用例）
      |
      v
任务类型注册（RE 修复、RV 检视、后续新类型）
      |
      v
任务状态机与阶段处理器
      |
      +--------------------+
      |         |          |
      v         v          v
Codex Runner  Forge      通知
      |         |          |
      +---------+----------+
                |
                v
SQLite 租约 / 工作目录 / 凭据 / 模型代理 / 签名发布
```

### 5.1 入口层

`web/app.py` 最终只负责 FastAPI 应用装配、共享依赖和生命周期。用户、仓库、Issue、任务、PR 检视和系统配置拆分为独立路由模块。

网页、飞书和未来的 API 只负责解析输入、鉴权和呈现结果，不直接编排任务或操作平台。

### 5.2 应用服务层

应用服务承载派发 Issue、关闭任务、同步反馈、创建 PR 检视等用例。所有入口调用相同服务，确保权限、校验、幂等和错误行为一致。

应用服务负责定义事务边界，但不包含 Codex 提示词和具体平台 HTTP 实现。

### 5.3 任务类型与状态机

一种任务类型由四部分定义：

- 输入定义（触发所需的参数和校验规则）；
- 阶段序列（固定的有限阶段，每个阶段一个独立处理器）；
- 产物规格（每个阶段必须持久化的结构化产物）；
- 通知规则（各状态变化对应的飞书和页面呈现）。

编排器只负责读取当前状态、调用阶段处理器、持久化结果和选择下一状态，不承担阶段的实现细节。

Issue 修复（RE）和 PR 检视（RV）是最先注册的两个任务类型；RE 的阶段序列固定为：

```text
准备工作区
-> 开发与自测
-> 双 Reviewer 检视
-> 集中修正
-> 提交前封装检查
-> 发布 PR
-> 等待人工审核
```

后续新任务类型（如依赖升级、CI 失败诊断）以同样方式注册，不修改基建代码。

### 5.4 Forge 边界

定义一个面向业务用例的稳定 Forge 协议，覆盖：

- 仓库与 Issue 元数据读取；
- Fork 创建和身份确认；
- 分支发布和 PR 创建、查询；
- PR 元数据、差异和评论操作。

GitHub 和 GitCode 分别实现该协议。现有 `provider`、`publisher` 和 `forge` 中重叠的网络、错误处理及模型转换逐步迁入平台适配器，迁移期间保持原接口兼容，不一次性重写。做完后接入新平台只需新增一个协议实现。

### 5.5 基础设施层

继续保留 SQLite 租约、通知 outbox、加密凭据、独立工作目录、模型短期凭据代理和签名发布。上层只能通过窄接口使用这些能力，不能直接依赖其存储细节。

## 6. Agent 质量机制

### 6.1 开发 Agent 六阶段闭环

开发 Agent 对问题分析和代码修改负完整责任，系统不增加重复分析的主管 Agent。

1. **仓库理解**：读取 Issue、贡献指南、`AGENTS.md`、构建配置和相关代码，识别语言、依赖和测试入口。
2. **问题复现**：优先执行现有测试或建立最小复现；无法复现时记录原因和替代验证方式。
3. **根因与方案**：在修改代码前输出根因、影响范围、修改方案、风险和测试计划。
4. **实现与局部验证**：完成修改并运行最相关测试，在开发阶段内部修复普通编译和测试错误。
5. **回归验证**：执行时间预算内最大合理测试集，记录命令、退出码、耗时和摘要。
6. **提交前自检**：检查差异范围、敏感信息、无关文件、生成物和工作树状态。

每个检查点生成结构化产物并持久化。没有满足前一检查点的最低输出要求时，不进入下一阶段。

### 6.2 双 Reviewer 分工

- 正确性 Reviewer 检查根因匹配、边界条件、并发、安全和兼容性。
- 测试 Reviewer 检查复现可信度、覆盖范围、回归风险和未验证路径。

两个 Reviewer 使用独立上下文检查实际代码和测试证据。系统对意见进行结构化校验、合并和去重，开发 Agent 最多集中修正一次。

已经修复的 Reviewer 意见不进入 PR 遗留问题。仍未解决的问题随 PR 一并提交，供人工审核继续处理。

### 6.3 证据化报告

PR 中的六段中文报告继续使用：问题描述、问题复现、修改方案、修改验证、测试回归和遗留问题。

报告由结构化执行产物生成，并明确区分：

- Agent 的分析结论；
- 系统实际执行的命令和结果；
- 未执行或无法完成的验证；
- Reviewer 检出但修正后仍存在的问题。

## 7. 可靠性与诊断

### 7.1 任务事件

在现有任务当前状态之外，增加只追加的任务事件记录。每个事件包含任务、阶段、运行编号、时间、执行者、结果、耗时、错误代码和脱敏摘要。

任务状态用于调度，任务事件用于审计和诊断。不得通过修改历史事件来伪造新的当前状态。

### 7.2 错误分类

错误至少分为以下类别：

- 输入或目标无效；
- 平台身份或权限不足；
- 网络和外部服务暂时不可用；
- 仓库依赖或构建失败；
- Agent 输出格式无效；
- 测试失败；
- 工作区、补丁或模型用量超限；
- 执行器中断或租约丢失；
- 外部副作用结果不确定；
- Coderus 内部错误。

错误代码保持稳定，页面和飞书可以显示不同文案，但不能依赖异常字符串判断恢复动作。

### 7.3 恢复规则

| 场景 | 处理方式 |
| --- | --- |
| Agent 启动前发生暂时性资源错误 | 有上限地自动重试 |
| Agent 执行中服务重启 | 标记本次运行中断，从当前安全阶段重跑 |
| 推送或创建 PR 结果不确定 | 先按固定分支和发布意图对账 |
| 输入、权限或仓库自身问题 | 进入需人工处理，不无限重试 |
| Reviewer 仍发现问题 | 集中修正一次后提交 PR 并记录遗留问题 |
| 任务被人工取消 | 终止进程、回收租约并保留诊断证据 |

### 7.4 轻量可观测性

- 使用结构化 JSON 日志并包含任务编号、阶段和运行编号。
- 内置最近 24 小时成功率、平均耗时、队列长度、失败分类和模型使用量。
- 展示模型服务、GitHub、GitCode、飞书、数据库、磁盘和调度器状态。
- 支持生成不包含凭据、个人路径和仓库源码的脱敏诊断包。
- 严重故障和持续积压通过飞书通知管理员。

## 8. 控制面板

控制面板继续采用面向日常工作的紧凑界面。

### 8.1 工作台

按仓库展示排队、运行、需人工处理、等待审核和异常任务，并保留全部仓库视图。默认隐藏已完成和已关闭任务。

### 8.2 任务详情

展示当前阶段、阶段耗时、Agent 心跳、任务事件时间线、测试结果、Reviewer 结论、PR 状态和脱敏执行证据。

页面根据任务状态只展示合法操作，例如取消、重新执行当前阶段、从安全检查点恢复或关闭任务。

### 8.3 系统诊断

系统页集中展示组件状态、配置完整性、平台权限、磁盘空间、SQLite 完整性、备份状态和最近发布记录，并提供对应处理建议。

## 9. 飞书助手演进

### 9.1 现状

助手已上线：基于模型代理做单轮自然语言问答，上下文为数据库只读快照（任务统计、最近任务、仓库、被引用任务详情），带防提示注入约束，任何失败降级为固定回复。

### 9.2 下一步

- **确认式命令代填**：助手识别用户意图后生成对应命令（如"帮我派发这个 Issue"→ 生成 `派发 <URL>`），由用户确认后才执行；助手本身始终不持有写权限。
- **上下文扩展**：任务事件上线后，助手可回答"任务为什么失败""卡在哪个阶段"等诊断类问题，数据来源仍为只读快照。
- **边界不变**：只读访问、防注入、失败降级三条约束在任何演进中保持不变。

## 10. 开源体验

### 10.1 使用路径

1. 快速体验：初始化本地服务并运行环境诊断，不要求真实平台 Token。
2. 接入仓库：配置模型与代码平台凭据，添加授权仓库并验证权限。
3. 正式运行：按需配置飞书、HTTPS 反向代理、自动备份和版本升级。

### 10.2 稳定命令

命令行逐步收敛为：

```text
coderus init
coderus doctor
coderus serve
coderus backup
coderus upgrade
```

`coderus doctor` 检查运行时版本、模型服务、代码平台权限、目录权限、磁盘空间、SQLite、飞书和公网安全配置。

### 10.3 首次配置

首次登录后的向导依次完成模型服务、代码平台账号、第一个授权仓库、可选飞书机器人和最终环境检查。向导与系统配置页面复用同一应用服务。

### 10.4 开源工程

- 使用语义化版本并维护 `CHANGELOG.md`。
- CI 覆盖 Python 3.12/3.13 和 Linux/Windows。
- 发布签名源码包和校验信息。
- 提供快速开始、故障排查、安全配置、升级回滚和贡献文档。
- 提供不会推送分支或创建 PR 的 dry-run 验证流程。
- 默认不收集遥测，未来只能由管理员明确选择加入。
- 仅开放 Forge 扩展协议，不建设通用插件市场。

## 11. 实施路线

### 阶段 0：建立基线

交付：

- 选择 10 至 20 个历史 Issue 形成固定评测集；
- 固定模型、提示词、资源限制和运行环境；
- 记录完成率、测试通过率、人工修改量、耗时和模型使用量；
- 补充服务重启、模型超时和 PR 创建结果不确定的端到端测试。

验收：后续工作流或提示词变更都能与统一基线比较。

### 阶段 1：架构收敛

交付：

- 拆分 `web/app.py` 为路由模块与装配文件，抽取应用服务层，网页和飞书改调应用服务；
- 拆分 Issue 阶段处理器，编排器只保留状态读取、处理器调用和状态转移；
- 收敛 Forge 协议，合并 `providers`、`publisher`、`forge` 的重叠实现和平台错误模型；
- 保持现有页面、URL、数据库和任务行为兼容。

验收：现有测试和端到端流程全部通过，各任务阶段可以独立测试，不引入通用框架。

### 阶段 2：可靠性与诊断

交付：

- 任务事件和稳定错误代码；
- 重启恢复、阶段重试、发布对账和通知补偿；
- 任务时间线、执行证据、系统诊断和脱敏诊断包。

验收：用户能够从页面判断失败阶段、原因和下一步；强制停止服务后不会重复创建 PR 或永久卡住任务。

### 阶段 3：Agent 效果

交付：

- 开发 Agent 六阶段闭环；
- 双 Reviewer 职责分离；
- 证据化 PR 报告；
- 一键重放固定评测集。

验收：有效修改率相对基线提升，普通构建错误不再进入 Reviewer，PR 报告与实际测试证据一致。

### 阶段 4：任务类型注册

交付：

- 任务类型接口：输入定义、阶段序列、产物规格、通知规则；
- RE 和 RV 迁移为注册的任务类型，行为保持不变；
- 新增一个试点任务类型（候选：依赖升级、CI 失败诊断）验证接口完备性。

验收：试点任务类型的接入不修改调度、租约、工作区、凭据、通知和发布等基建代码；RE 和 RV 全部既有测试通过。

### 阶段 5：助手演进

交付：

- 飞书助手确认式命令代填和诊断类问答。

验收：助手代填的每个写操作都留有人工确认记录，助手在任何演进中保持只读访问。

### 阶段 6：开源体验

交付：

- `coderus doctor`、首次配置向导和 dry-run；
- `coderus init` / `coderus serve` / `coderus backup` / `coderus upgrade` 命令收敛；
- Linux/Windows CI 矩阵；
- 语义化版本、升级说明和完整运维文档。

验收：新用户能够在 15 分钟内启动控制面板并通过环境诊断，配置凭据后能够完成一次测试任务。

## 12. 指标

核心指标包括：

- Issue 复现成功率；
- 有效修改率和测试通过率；
- 无需人工改代码即可进入审核的 PR 比例；
- 每个任务的人工修改量；
- 任务完成时间和各阶段耗时；
- 模型请求量、Token 和费用；
- 自动恢复成功率；
- 重复 PR 数量；
- 无法解释或永久卡住的任务数量；
- 新任务类型接入的改动范围（应不触碰基建代码）；
- 助手回答的采纳率和降级率。

指标用于比较相同评测环境下的版本，不以单次任务结果代替趋势判断。

## 13. 迁移与风险控制

- 架构拆分前先建立行为测试，不在同一变更中同时重构和改变业务规则。
- 数据库变更保持向后兼容，并通过现有签名发布、备份、Schema 门禁和回滚流程上线。
- 平台适配层逐个用例迁移，GitHub 和 GitCode 的实际行为均需要契约测试。
- 任务类型接口先以 RE、RV 迁移验证，再开放给新类型；接口不满足时优先修接口而不是让类型绕过基建。
- 新任务事件和指标必须脱敏，不保存平台 Token、模型 Key、个人主机路径或完整仓库源码。
- Agent 提示词或模型变更必须先运行固定评测集，再决定是否进入正式版本。
- 每个阶段独立发布，出现回归时回滚该阶段，不把多个阶段绑定为一次大版本切换。

## 14. 决策结论

Coderus 下一阶段以"自动化工作平台"为方向，采用"先收敛、后平台化"的演进路线：立即从阶段 0（评测基线）和阶段 1（架构收敛）开始，在架构与可靠性稳定后实施任务类型注册，使新的自动化任务能够以最小成本接入统一基建；开源体验作为收尾阶段持续投入，内部使用版和开源版保持同一套代码。
